# CED on the PP5 production partition

## Scope

The initial validation below uses `port/dsv41f-hybrid`, PP5 `8,8,8,8,8`, TP1,
text, DSpark disabled and CUDA Graph decode. The distributed DSpark extension
and its serving A/B are recorded at the end. CED remains opt-in and mutually exclusive with
`dsv41_fast_prefill`. It approximates decoder prefill by replaying only the
encoder suffix; equivalence to a full unbounded prefill is not claimed.

## Execution and state

| Rank | Layers | CED prefill work |
| --- | --- | --- |
| PP0 | 0–7 | Every scheduled token |
| PP1 | 8–15 | Every scheduled token |
| PP2 | 16–23 | Full 16–19; publish layer-20 main/index KV for every token; replay 20–23 on the final suffix |
| PP3 | 24–31 | Import complete layer-20 KV; replay its local layers on the final suffix |
| PP4 | 32–39 | Import complete layer-20 KV; replay and scatter outputs back to scheduler rows |

The replay retains up to 128 encoder rows per request across chunk boundaries.
Each PP stage completes the deferred mHC post operation before forwarding the
replay stream. Full-chunk main KV and normalized index K remain separate from
replay hidden states, pre-mix and query-specific top-k/candidate rows.

A short final chunk can have two scheduled rows and 128 replay rows. Ordinary PP
buffers keep their scheduler shapes; additional tensors preserve the full replay
shape. The model runner accepts these dynamically sized tensors only for eager
calls. Pure decode retains the existing static PP buffers and captured graph.

Replay metadata uses independent builders and retains source-layer keys. Global
sequence lengths and absolute positions remain unchanged; only the local SWA
prefill gather is clamped to the computed suffix.

## Configuration used for the CED on/off comparison

```bash
PORT_MAX_BATCHED=1024 PORT_DSPARK_TOKENS=0 PORT_MM_IMAGES=0 \
  PORT_FAST_PREFILL=0 PORT_PORT=26662 \
  PORT_EXTRA_ARGS='--additional-config {"ced_prefill":true}' \
  benchmarks/deepseek_v4_1/run_port_pp5.sh
```

Prefix caching must be disabled. The initial implementation rejected distributed
DSpark; the extension below supplies its draft-context relay. Prompt-logprob requests use full
prefill; if a mixed batch's full rows plus retained suffixes exceed the worker
row capacity, CED rejects the batch with an explicit capacity error. For the
validated text-only configuration, `max_num_seqs=8`, window 128 and batch
capacity 1024 bound ordinary CED replay to 1024 rows.

## Verification

Evidence: `profiles/deepseek_v4_1/20260927_ced_pp5_ab/`.

- CED and fast-prefill suites: 71 passed, 14 warnings.
- Split decoder versus unsplit CED: exact mocked arithmetic for final chunks of
  1, 2 and 128 rows, including mHC reconstruction and full KV exports.
- Metadata source-key retention with independent builders.
- Existing suffix isolation, mixed decode/prefill, cleanup and prompt-logprob
  fallback coverage. The existing Engram fixture now calls the layer's `_forward`
  implementation so it tests PP-boundary arithmetic without a profiling wrapper.
- Real-GPU A/B: DSpark, fast-prefill and prefix caching disabled in both arms.
  Same three 32768-token prompts, greedy sampling, exactly 256 output tokens.
  One 32K warmup is excluded. Short-final-chunk and concurrent retrieval requests
  precede timing. The CED warmup records per-layer executed rows; timed repeats
  do not enable row tracing.
- `FULL` is requested; the attention backend selects `FULL_DECODE_ONLY`.
  The reported prefill duration is streaming TTFT, not a kernel-only timer.
  Decode throughput uses the 255 intervals after the first generated token.

## Measured result

Medians over three measured requests per arm:

| Metric | CED off | CED on | Observed change |
| --- | ---: | ---: | ---: |
| Prefill / TTFT | 5.951524 s | 5.422712 s | -8.89% |
| Prefill throughput | 5505.82 token/s | 6042.73 token/s | +9.75% |
| Decode throughput | 39.27 token/s | 41.38 token/s | +5.39% |
| Request wall time | 12.417367 s | 11.584125 s | -6.71% |

All three timed long-context retrievals pass in each arm, with exact 32768 input
and 256 output counts. The 1026-token short-final-chunk request and two concurrent
1026-token requests also return their own markers without cross-talk in both
arms. The 32K warmup passes as well. These are retrieval checks, not a general
quality evaluation: forcing 256 tokens after a short answer produces extra,
sometimes repetitive continuation.

The CED warmup row trace confirms 32768 rows per layer for 0–19 and 128 replay
rows per layer for 20–39. Layer 20 additionally publishes full-prompt main/index
KV outside its ordinary attention/FFN forward. All five ranks capture decode
graphs successfully; no CUDA errors were observed. Prefix-cache hits remain zero.

The demonstrated CED benefit is reduced prefill and request latency. Pure decode
code is unchanged; different CED outputs and runtime variation can affect the
observed decode rate, so its increase is not attributed to a decode optimization.
This A/B uses unbounded prefill as the baseline; it does not establish an
advantage over the launcher's separately enabled fast-prefill mode.

Detailed per-run values, output text, server logs, row traces, source hashes and
test logs are retained beside `summary.json` in the evidence directory above.
CED remains opt-in. The command above pins the 1024-token chunk used for this
comparison; the subsequent chunk-size comparison is recorded below.

## Default prefill chunk: 1024 to 2048

The PP5 launcher now defaults `PORT_MAX_BATCHED` to 2048. The CED-on comparison
kept DSpark, fast-prefill and prefix caching disabled in both arms. It used the
same three 32K/256 greedy prompts and a fresh 32K warmup per arm. The 1024 arm
explicitly set `PORT_MAX_BATCHED=1024`; the 2048 arm left it unset, and the
server log confirms 2048. Evidence: `profiles/deepseek_v4_1/20260927_ced_chunk2048_ab/`.

| Metric, median of three | 1024 | 2048 | Observed change |
| --- | ---: | ---: | ---: |
| Prefill / TTFT | 5.354210 s | 4.439601 s | -17.08% |
| Prefill throughput | 6120.04 token/s | 7380.84 token/s | +20.60% |
| Decode throughput | 40.23 token/s | 40.99 token/s | +1.89% |
| Request wall time | 11.689359 s | 10.663322 s | -8.78% |

All three 32K requests per arm returned the expected passphrase and exactly 256
output tokens. Both arms also passed a 2050-token prompt, whose last chunk has
two tokens under 2048, and two concurrent 2050-token prompts without cross-talk.
All five ranks captured decode graphs; the backend again selected
`FULL_DECODE_ONLY`. No runtime OOM or CUDA error occurred in this DSpark-off test.
The measured decode difference is observational; this setting primarily changes
prefill scheduling. Earlier DSpark-enabled 2048 runs exhausted PP2 headroom, so
this comparison does not establish safety for distributed DSpark at 2048.

## Distributed DSpark extension

CED now supports the production distributed draft layout: PP1/PP2/PP3 own the
three draft blocks and PP4 owns the projection and Markov head. Fast-prefill
must be disabled. The previous guard is removed after adapting context transport:

1. PP4 retains the complete CED auxiliary suffix, including rows from preceding
   chunks. Only final CED prefill requests contribute; mixed decode rows and
   full-prefill fallbacks keep the ordinary rejection-aware context insertion.
2. The head casts the retained mHC states to the draft model dtype before its
   context projection, matching the ordinary BF16 workspace. Direct FP32 input
   failed Marlin during the first mixed warmup; a regression test covers this.
3. Projected suffix states, absolute positions and batch request indices travel
   through the existing PP4 -> PP1 -> PP2 -> PP3 relay. Each stage reconstructs
   physical slots from its own current draft block tables and layer/group map;
   saved head-side slots are not transferable and may also be evicted.
4. Each draft stage inserts the suffix after its ordinary scheduler-row context
   and before its query graph. This prevents CED padding from overwriting the
   retained history and handles a one-row final chunk with a 128-row suffix.
   PP3 removes the suffix payload before returning query states to PP4.

Pure decode retains the existing relay and graph execution. Additional tensors
are sent only when CED finishes a prefill. Prefix caching remains unsupported.

### PP5 A/B at batch budget 2048

Evidence: `profiles/deepseek_v4_1/20260927_ced_distributed/report.md`,
`summary.json`, raw outputs, logs and source hashes in the same directory.
Both arms use q5 greedy, FULL draft graphs, target FULL_DECODE_ONLY,
FP8 KV, eight maximum sequences, no prefix cache or fast-prefill, and the three
strict numeric switches. One fixed 32768-token prompt, 256 output tokens,
one excluded warmup and five timed requests per arm; only B enables CED.

| Metric, median of five | CED off | CED on | Change |
| --- | ---: | ---: | ---: |
| TTFT | 6.640400 s | 4.941016 s | -25.59% |
| Decode throughput | 66.36 token/s | 84.18 token/s | +26.86% |
| Request duration | 10.508202 s | 7.941283 s | -24.43% |
| Draft rounds | 52 | 44 | -15.38% |
| Accepted / drafted | 203 / 260 (78.08%) | 211 / 220 (95.91%) | +17.83 percentage points |
| Position-0 acceptance | 100% | 100% | unchanged |

All ten outputs are identical token by token and contain no EOS tokens.
Acceptance counters are identical within each arm. The throughput gain includes
fewer verification rounds. The measured per-round median also falls from 73.90
to 68.84 ms, but the two services are separate instances; that difference is not
attributed to a decode-kernel optimization. CED is approximate, so equality on
this pinned sample does not imply general equivalence to unbounded prefill.

The excluded warmup records 32768 rows per layer for 0–19 and exactly 128 rows
per layer for 20–39. All target ranks capture graphs; all four draft ranks
capture and replay their local graphs. Short final chunks of one and two rows
(2045/2046-token inputs with the 2044-row DSpark prefill chunk), two concurrent
retrieval requests and 32K retrieval all pass with no cross-talk. Arithmetic and
sorting checks also pass. These checks evaluate state handling and selected
outputs, not broad model quality. CPU regression suites: 107 passed; the relay
suite after the dtype correction: 36 passed. Ruff and diff checks pass.
